# 01 · DNS 是怎么工作的

> 这份文档的目标不是复述百科，而是让"为什么我的配置会把查询送到运营商那里"变得**可推导**。
> 读完之后你应该能自己回答：一次解析有多少个环节可能被第三方看到、所谓"加密 DNS"到底加密了什么、以及为什么"开了 DoH"仍然可能泄露。

---

## 1. 一句话定义

DNS 是互联网的**电话簿**：把人类可读的域名（`www.baidu.com`）翻译成机器可路由的 IP 地址（`110.242.68.66`）。

它有两个容易忽略的性质，正是所有泄露问题的根源：

- **它几乎总是明文的**（传统 DNS 走 UDP:53，无加密、无认证）。
- **它几乎总是"由别人替你去问"的**（递归解析，你只问一个"递归解析器"，它替你把整条链跑完）。

---

## 2. 一次递归解析的完整过程

当你的设备要解析 `www.example.com`，它自己是不知道答案的。它做的事是：**问一台"递归解析器"，请它替你跑完全程**。

```
你的设备（stub resolver）
   │  ① 问：www.example.com 的 A 记录是？
   ▼
递归解析器（Recursive Resolver）  ← 你配置的 DNS 服务器，比如 223.5.5.5
   │
   │  ② 根服务器："com 的权威服务器在哪？"
   ├──────────────► 根服务器 (a.root-servers.net 等 13 组)
   │  ◄────────────── "去问 a.gtld-servers.net"
   │
   │  ③ TLD 服务器："example.com 的权威服务器在哪？"
   ├──────────────► .com TLD 服务器
   │  ◄────────────── "去问 ns1.example.com"
   │
   │  ④ 权威服务器："www.example.com 的 A 记录是什么？"
   ├──────────────► example.com 的权威服务器
   │  ◄────────────── "93.184.216.34"
   │
   ▼  ⑤ 把答案给你（并缓存一段时间 = TTL）
你的设备
```

**能从这里读出的第一个结论：**
在第 ②–⑤ 步里，有**四台不同的服务器**看到了"有人在查 `www.example.com`"。而在第 ① 步，**递归解析器**也看到了。

于是问题变成：**这五台里，哪几台能看到"是你"在查？**

- 第 ②–④ 步看到的是**递归解析器的 IP**，不是你。也就是说，只有递归解析器知道"是你问的"。
- 第 ① 步看到的是**你的 IP**。

⇒ **谁是你的递归解析器，谁就知道你在访问什么。** 这就是"DNS 泄露"这句话真正的内容 —— 它泄露的不是"某个域名被查了"，而是**"你在用哪台解析器"**，以及这台解析器可以把你的查询和你本人关联起来。

---

## 3. 明文 DNS 的暴露面

传统 DNS（UDP:53）在这三个位置会被旁观或篡改：

| 位置 | 谁能看 | 能做什么 |
|---|---|---|
| **你的设备 ↔ 递归解析器** | 你的接入网（运营商 / 公共 Wi-Fi） | 看到**完整的域名**；可以丢弃、可以返回伪造应答 |
| **递归解析器本机** | 解析器运营方 | 完整日志：查询域名 + 你的 IP + 时间 |
| **递归解析器 ↔ 权威服务器** | 沿途网络 | 通常看到的是解析器 IP，但应答仍可被注入 |

> **"运营商 DNS 劫持"就发生在第 1 行。**
> 中国运营商对**第三方明文 :53** 普遍做**透明重定向**：你把包发给 `8.8.8.8:53`，它在链路上被改写成发给运营商的解析器。
> 表现上"你没配置错的服务器"，实际应答却来自运营商 —— leak test 上就会显示"DNS 泄露到中国电信"。
> 更隐蔽的是：即使重定向失败、查询超时，客户端通常会**回落 `system` DNS**，而 `system` DNS 恰恰是 DHCP 下发的运营商 DNS。**两条路都通向运营商。**

---

## 4. 加密 DNS：DoH / DoT / DoQ

加密 DNS 解决的是**"设备 ↔ 递归解析器"这一段**被旁观的问题。

| 协议 | 全称 | 端口 | RFC | 特点 |
|---|---|---|---|---|
| **DoH** | DNS over HTTPS | **443** | RFC 8484 | 伪装成普通 HTTPS，最难被识别/阻断；线上格式为 `GET /dns-query?dns=<base64url>` + `Accept: application/dns-message` |
| **DoT** | DNS over TLS | **853** | RFC 7858 | 独立端口，明文握手可见，易被识别与阻断 |
| **DoQ** | DNS over QUIC | **853/UDP** | RFC 9250 | 基于 QUIC，性能好但普及度低 |

**加密了，但没完全隐藏。** 即使使用 DoH，链路旁观者仍能看到：

- **你连的 IP**（例如 `8.8.8.8:443`）—— 知道你在用哪家解析器；
- **TLS SNI**（未加密的 ClientHello 里的主机名，除非用 ECH）—— 例如 `dns.google`；
- **流量特征**（包长、时序、连接频率）—— 能被用来做指纹识别。

⇒ **加密 DNS 保护的是"你查了什么域名"，不保护"你在用谁"。** 而在防"泄露到 ISP"这件事上，后者才是关键。

> **一个实用的坑**：RFC 8484 只强制**线格式**（`?dns=<base64url>` + `Accept: application/dns-message`）。
> `?name=x&type=A` + `Accept: application/dns-json` 是 Google 风格的**可选** JSON API，很多服务器会直接返回 400。
> **用 JSON API 测端点死活会误判端点是坏的。** 本仓库的 `probe_doh.py` 用的就是线格式。

---

## 5. 为什么"开了加密 DNS"还会泄露

因为配置里通常不止一条解析路径。一条加密路径**失败**时，软件会按回退链往下走 —— 而回退链的末端，往往就是明文。

Egern 官方文档给出的回退链：

> `bootstrap` …… 仅支持传统 UDP 协议（端口 53），且**不遵循代理规则 —— 流量直连**。
> 用途：① 解析 `upstreams` 中加密 DNS 服务器的主机名；② 作为最终的 DNS 回退。
> `bootstrap` …… **未配置或解析失败时，自动使用系统 DNS 服务器。**

画成链路：

```
你配置的加密上游（DoH :443 / DoT :853）
        │  失败（超时、被阻断、域名解析不了……）
        ▼
bootstrap（明文 UDP:53，直连）
        │  失败（被运营商接管 / 被丢包）
        ▼
system DNS（= DHCP 下发的运营商 DNS）
```

**这三行就是全部答案。** 任何一次解析只要落到第 2 行或第 3 行，就能被记为"泄露到 ISP"。

于是防御思路只有一条：**别去优化第 2 行，而是让它永远用不上。**

---

## 6. 系统 DNS 与运营商 DNS 是怎么进来的

- **`system DNS`**：设备从 DHCP（Wi-Fi/蜂窝）里拿到的 DNS 服务器地址。在家庭宽带下通常是路由器，在蜂窝下**通常是运营商自己下发的解析器**。
- **它在配置里的地位**：几乎所有代理软件都把它当作"最后的兜底"。**一个不会失败的兜底是不存在的** —— 只要你配置的上游有可能失败，这条兜底就有可能被触发。
- **透明重定向**：运营商在链路上改写目的地址，把你发往任意外部 `:53` 的查询截获到自己的解析器。**这就是为什么"把 bootstrap 换成一个更干净的 IP"通常无效** —— 包在运营商的线路上被接管了。

> 想验证"这条路真实的递归出口是谁"，可以问一个会回显解析器出口 IP 的域名：
> ```bash
> nslookup -type=A whoami.akamai.net 223.5.5.5
> # 返回的 IP 就是 Akamai 看到的"解析器出口 IP"
> ```
> 用它做对比：如果走加密路径和走明文路径返回的出口 IP 不同，说明两条路确实经过不同的解析器。

## 7. Fake IP：为什么代理软件要这么做，以及它的副作用

**为什么需要**：有些应用（尤其是系统组件）会在代理还没决定如何路由之前就发起解析。没有 Fake IP，代理软件就必须**先解析**才能按 IP 分流 —— 那等于每次访问都产生一次真实解析（并且可能走明文）。

**怎么做**：`hijack_dns: ['*']` 接管 `:53`，对命中的域名返回一个**保留地址段**里的假 IP（常见 `198.18.0.0/16`），并把"假 IP ↔ 真域名"记在内存里。当连接真的打到这个假 IP 时，代理软件就能反查出域名，从而**按域名**分流。

**副作用**：
- 被 Fake IP 映射的域名**永远不会真正解析**，所以"某些依赖真实 IP 的功能"会异常（例如 macOS/iOS 的推送、AirPlay、内网发现）。这些域名需要放进 `real_ip_domains` 放行。
- 只有 **`:53`** 会被接管。**DoH（`:443`）不会被接管** —— 如果某个 App 自带 DoH，它会直接绕过你的 `hijack_dns`。

## 8. Egern 的双轨 DNS 模型

Egern 有**两条互不相通**的解析路径。**不理解这个，就会改错地方。**

| 路径 | 用途 | 连接上游时 | 未命中时 |
|---|---|---|---|
| **默认 DNS** | 解析**用户要访问**的域名 | **遵循代理规则**（可以走代理） | 回退 `bootstrap` |
| **代理 DNS** | 官方措辞是"供代理服务解析目标域名"；从"**强制直连**"这个约束反推，它实际承担的是**节点 `server` 的域名** —— 那个名字必须在隧道建立**之前**解析出来 | **强制直连**（避免 DNS→代理→DNS 的循环依赖） | 未配 `proxy_nameservers` 时，回退 `bootstrap` |

⭐ **"强制直连"这条约束是理解一切的关键。**

在国内，直连去问境外解析器（`8.8.8.8:443` 之类）基本不通。所以：

> **代理侧的任何解析，只有两条出路：国内解析器，或者明文 `bootstrap`（进而可能回落 `system` = 运营商）。**

这条路径**无法加密**。收口只有两个办法：

1. **让它不需要解析** —— 把节点 `server` 写成 IP 字面量（根治，首选）；
2. **给它一个确定可达的解析器** —— 让代理 DNS 落在国内加密组上。有两条**互斥**的写法：
   - **显式写 `proxy_nameservers`**（本模板采用）：官方语义是「所有代理 DNS 查询强制走该列表、
     **`forward` 规则被跳过**」，那条"未命中回退 `bootstrap`"的分支在结构上不再存在；
   - **不写 `proxy_nameservers`**：代理 DNS 与默认 DNS 共用 `forward` 规则，靠 `forward` 的兜底接住。

> ⚠️ **这两条不能叠加。** 一旦写了 `proxy_nameservers`，`forward` 里的规则对节点域名**完全不起作用**
> （代理 DNS 根本不查 `forward` 阶段）。所以"在 `forward` 里为节点域名加一条 `domain_suffix → 国内加密组"
> 这个曾经有效的做法，**自 f7 引入 `proxy_nameservers` 起就是死代码** —— 加上去也不会被查询到。
> f10 又把 `forward` 塌缩成纯兜底，即使不写 `proxy_nameservers`，节点域名也已经命中兜底。
> ⇒ 今天还值得做的只有：**节点 `server` 写成 IP**；若域名被污染导致连不上，再用 `hosts` 把它钉到 IP。

**社区事实标准配置（Repcz）有一句比官方文档更实用的话：**

> 「Egern 的解析规则接近 Surge，即**已经匹配到走节点的规则交由节点 DNS 查询，`dns` 设置仅对需要本地解析的域名进行查询**」

⇒ **进代理的域名由节点远端解析；本地 `dns:` 段只服务「直连域名」和「代理节点自己的域名」。**
这决定了改哪里才有意义：**优化本地 `dns` 段，只对 DIRECT 域名和节点域名有效。**

## 9. `no_resolve`：用解析换分流的开关

官方 `rules` 文档原文：

> `no_resolve (bool)`，可选 —— 仅适用于 IP 类规则（`geoip`、`ip_cidr`、`ip_cidr6`、`asn`）。
> **设为 `true` 时仅匹配已解析的 IP 地址，不会触发 DNS 解析。**

这句话的反面同样成立，而且是全部事故的来源：

> **不带 `no_resolve` 的 IP 类规则，会为了判断"这个连接是不是落在我的网段里"，而触发一次 DNS 解析。**

**它有三个层级，别混：**

| 层级 | 写法 | 作用范围 |
|---|---|---|
| **规则级** | `rules:` 里的 `- geoip: {match: CN, policy: DIRECT, no_resolve: true}` | 官方明说**只适用 `geoip`/`ip_cidr`/`ip_cidr6`/`asn` 四类**；写在 `rule_set` 规则上**不生效** |
| **规则集文件顶层** | Egern 原生 YAML 规则集里的 `no_resolve: true` | 影响该文件内所有 IP 相关规则 |
| **规则集条目级** | Surge `.list` 里的 `IP-CIDR,x/y,no-resolve` | **第三方 `.list` 走的就是这一层** —— 也是缺陷最常藏身的地方 |

**代价（非常重要）**：给 `geoip: CN` 加上 `no_resolve` 之后，**它不再匹配域名**。
一份"本来靠 `geoip: CN` 强制解析一次、判出 CN IP 再 DIRECT"的配置，加上 `no_resolve` 后：

- ✅ 泄露治好了（不再有强制解析）
- ❌ **国内域名的直连路径一起消失了**，整片落到 `default` → 走代理

⇒ **改 `no_resolve`，必须成对交付一份"域名条目足够多"的国内 DIRECT 规则集。** 详见 [docs/05](05-分流与no_resolve必须成对交付.md)。

## 10. 自测方法

| 目的 | 方法 |
|---|---|
| 看解析器出口在哪 | `nslookup -type=A whoami.akamai.net <解析器>`，返回的就是 Akamai 看到的出口 IP |
| 看是否泄露给 ISP | 在**目标链路**（尤其是蜂窝流量）上跑 dnsleaktest / browserleaks，看结果里的 AS 归属 |
| 看某次解析走了哪条路 | 看客户端日志里的 `upstream` 字段。出现 `bootstrap` / `system` 就是走到了明文回退分支 |
| 判断某个域名走了直连还是代理 | 看连接日志里该域名命中的规则与策略 |

> ⚠️ **测试环境的链路必须写清楚。** 家庭 Wi-Fi（有旁路由/OpenClash）与运营商蜂窝是**两套完全不同的网络环境**：
> 家用旁路由可能把明文 `:53` 全量劫持到 Fake IP，而蜂窝下明文 `:53` 会被运营商透明重定向。
> **用 A 链路的实测去解释 B 链路的现象，整轮结论会作废。**
