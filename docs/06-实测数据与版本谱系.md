## 1. 加密 DNS 端点逐个实测

命令：`python skill/scripts/probe_dns_endpoints.py Profile.yaml`
（DoH 用 RFC 8484 **线格式** `GET /dns-query?dns=<base64url>` + `Accept: application/dns-message`；DoT 做 853 握手并校验证书）

### 1.1 国内端点（作为 `Domestic-DNS`）

| 端点 | DoH 线格式 | DoT 证书 | 结论 |
|---|---|---|---|
| `223.5.5.5` | ✅ HTTP 200 + 有效 A 记录 | — | 可用 |
| `223.6.6.6` | ✅ HTTP 200 + 有效 A 记录 | — | 可用 |
| `1.12.12.12` | ✅ HTTP 200 + 有效 A 记录 | — | 可用 |
| `120.53.53.53` | ✅ HTTP 200 + 有效 A 记录 | — | 可用 |
| `tls://223.5.5.5` | — | ✅ `CN=*.alidns.com`（**覆盖 IP**） | 可用 |
| `tls://1.12.12.12` | — | ✅ `CN=120.53.53.53`（**覆盖 IP**） | 可用 |

⇒ **2 家机构 × 2 种协议 × 各 2 个 IP = 6 个端点**，任一组合存活该组就不会"全失败"。

### 1.2 境外端点（作为 `Foreign-DNS`）

| 端点 | 结果 | 结论 |
|---|---|---|
| `https://8.8.8.8/dns-query` | ✅ HTTP 200 | 可用 |
| `https://8.8.4.4/dns-query` | ✅ HTTP 200 | 可用 |
| `https://1.1.1.1/dns-query` | ✅ HTTP 200 | 可用 |
| `https://1.0.0.1/dns-query` | ✅ HTTP 200 | 可用 |
| `https://9.9.9.9/dns-query` | ❌ **`HTTP Version Not Supported`** | **不可用 —— 必须改 DoT** |
| `https://149.112.112.112/dns-query` | ❌ 同上 | 同上 |
| `tls://8.8.8.8` | ✅ | 可用 |
| `tls://9.9.9.9` | ✅ `CN=dns.quad9.net` | 可用 |

**关键结论：Quad9 在 `9.9.9.9` 上只提供 HTTP/3，不响应 HTTP/1.1 线格式 ⇒ 写 `https://9.9.9.9/dns-query` 会静默失效。**

**总计：15 个端点，修掉 Quad9 的协议后 0 失败。**

> ⚠️ **必须用线格式测，不能用 JSON API。**
> RFC 8484 只强制线格式（`?dns=<base64url>`）。`?name=x&type=A` + `Accept: application/dns-json` 是 Google 风格的**可选** API —— `dns.google` / `8.8.8.8` / `dns.alidns.com` 用 JSON 都会返回 400，**它们没有坏**。用 JSON API 判死活会得出完全错误的"端点不可用"清单。

## 2. 国内解析器解境外域名 → 污染实测

问题：把境外域名交给国内解析器，会拿到什么？
方法：分别向各端点请求 `www.google.com` 的 A 记录。

| 端点 | RFC8484 线格式 | JSON API | `www.google.com` 返回 | 判读 |
|---|---|---|---|---|
| `doh.18bit.cn` | 200 ✅ | 400 | `216.239.38.120` | 基本可信 |
| `dns.alidns.com` | 200 ✅ | 400 | **`31.13.92.37`** | ❌ **Facebook 网段 —— 典型 GFW 污染签名** |
| `doh.pub` | 200 ✅ | 200 | `174.132.167.252` | 存疑 |
| `dns.google` / `1.1.1.1` / `8.8.8.8` | 200 ✅ | 400 / 200 | `142.251.x.x` | ✅ 真实地址 |

**结论：让国内解析器解境外域名，不是"泄露"这么轻 —— 是直接解析错（拿到污染 IP）。**

> ⚠️ **表中具体 IP 是单次观测，会随时间和链路漂移 —— 只看"是否落在污染段"，不要对照具体值。**
>
> 2026-09-20 复测即出现漂移：`dns.alidns.com` 返回 `174.132.167.252`、`doh.pub` 返回 `69.171.235.22`
> （Facebook 网段）—— 与上表的对应关系**恰好互换**。结论完全复现（**国内解析器解境外域名会拿到污染应答**），
> 但具体 IP 不可复现。判据是**是否落在已知污染段**（如 Facebook `31.13.x` / `69.171.x`），而非某个固定 IP。

### 这条结论的边界（很重要）

它**只约束"本地解析"这条路径**。官方 DNS 文档 + 社区共识：

> 已经匹配到走节点的域名由**节点远程解析**，本地 `dns:` 段只为"需要本地解析"的名字服务（DIRECT 域名、节点域名、profile 自身依赖）。

所以：

- ✅ **兜底组指国内，不会让"要访问的境外网站"拿到污染答案** —— 走代理的域名根本不经过本地 `dns` 段；
- ✅ 而且**"泄露到运营商"和"答案被污染"是两个不同的问题，致命的是前者**：前者不可撤销，后者对国内/Apple 域名反而更快更准。

⇒ **兜底组的唯一判据是「直连可达」，不是「指向境外」。**

## 3. `no_resolve` 相关实测

### 3.1 `Apple_All.list` 的 13 条裸 IP 条目

| 文件 | 条目总数 | 带 `no-resolve` 的 IP 条目 | 缺 `no-resolve` 的 IP 条目 |
|---|---|---|---|
| `Apple_All.list` | 1616 | 0 | **13** ❌ |
| `Apple_All_No_Resolve.list` | 1616 | 13 | 0 ✅ |

核对方式：去掉 `,no-resolve` 后两份文件**逐条相同** ⇒ 覆盖面零损失。

**全部 22 个被引用的远程规则集逐个下载核对后（含 2026-09-21 新增的 `white-guard` / `ads`）：只有 `Apple_All.list` 存在这个缺陷。**

## 4. 版本谱系（f1 → f8）

| 版本 | 改动 | 结果 |
|---|---|---|
| **f1** | 第一版加固 | ❌ 私自加了 `proxy_nameservers`，把代理侧解析钉死在国内 → **泄露从"偶发"变成"确定"** |
| **f2** | 端点改 IP 字面量 + 15 条 DNS 端点显式路由 + 加 `block_ips` | ❌ `proxy_nameservers` 仍在，问题未解 |
| **f3** | 删 `proxy_nameservers`；显式覆盖**节点域名**；`forward` 双兜底 | ✅ 修掉节点域名明文解析 ⚠️ 漏了 latency 测试域名 |
| **f4** | 补 3 条 **profile 自身必需解析**（两个延迟测试域名 + `jsdelivr`）→ 国内组 | ✅ 修掉"每轮测速触发一次"的持续泄露 |
| **f5** | `upstreams` 全部改 IP 字面量（国内 6 / 境外 6）+ `bootstrap` 扩到 3 个国内 IP | ✅ 消灭 `bootstrap` 用途① |
| **f6** | `forward` 两条兜底的 `value`：境外组 → 国内组 | ✅ 消灭 `bootstrap` 用途②（兜底不再依赖代理） |
| **f7** | ① `Apple_All.list` → `Apple_All_No_Resolve.list`；② 显式写 `proxy_nameservers`；③ 给 `geoip: CN` 补 `no_resolve` | ✅ 泄露治好（第③条是**真正的答案**）<br>❌ **但同一手把国内域名的直连路径一起关掉了** |
| **f8** | **只改一条**：`ChinaMax.list` → `ChinaMax_All_No_Resolve.list`（第 44 条规则） | ✅ **泄露与分流同时成立 —— 真机验收通过** |

### 每一版的验证结果

|---|---|---|---|
| f6 | 0 high / 3 low / 43 ok | ❌ **HIGH** | 未覆盖 |
| f7 | 0 high / 3 low / 43 ok | ✅ OK (20/20) | ❌ **7/15 国内探针落 Final** |
| **f8** | **0 high / 3 low / 43 ok** | ✅ **OK (20/20)** | ✅ **15/15 DIRECT** |

> f7 那一行是本项目最重要的一张表：**两个脚本双双全绿，配置却不可用。**

## 5. 五次「审计通过但实测有问题」

| # | 表现 | 真实原因 | 补上的审计维度 |
|---|---|---|---|
| 1 | f1/f2 脚本报 0 high | 靠**加配置压指标**（`proxy_nameservers`）掩盖了问题 | — |
| 2 | f3 脚本报 0 high | 审计器**没看 latency 测试域名**这一类 | 清单 15 |
| 3 | f5/f6 脚本报 0 high | **判据不足**：`group_ready` 只要求"端点全为 IP + 至少一个被判路由"，没要求那一条是 `DIRECT` | 收紧为 `group_reach` |
| 4 | f6 脚本报 0 high | **审计维度缺失**：只看 profile 文本，**没看它引用的规则集文件** | `audit_ruleset_noresolve.py`（清单 16） |
| 5 | f7 两个脚本都全绿 | **审计不覆盖分流** —— 治泄露的副作用没人检查 | `audit_routing_coverage.py`（清单 17） |

**固化下来的规则：**

> **任何一次「审计绿了但实测有问题」，都必须假设"存在审计器看不见的维度"，并把这个维度补成一个可复跑的脚本 —— 而不是重跑同一个脚本，也不是只解释为什么脚本是对的。**

## 7. 三个脚本怎么用

```bash
PY="<你的 venv>/Scripts/python.exe"      # 或系统 python3
S="skill/scripts"

# ① profile 层审计（清单 1–15）
"$PY" "$S/check_egern_dns.py" Profile.yaml

# ② 规则集层审计（清单 16）—— 会下载全部被引用的规则集并数条目
"$PY" "$S/audit_ruleset_noresolve.py" Profile.yaml
"$PY" "$S/audit_ruleset_noresolve.py" --url https://.../Apple_All.list   # 单文件模式
"$PY" "$S/audit_ruleset_noresolve.py" Profile.yaml --offline             # 只用缓存

# ③ 分流覆盖审计（清单 17）—— 域名 → 命中规则 → 策略
"$PY" "$S/audit_routing_coverage.py" Profile.yaml
"$PY" "$S/audit_routing_coverage.py" Profile.yaml --domain www.deepseek.com   # 指定域名

# 辅助
"$PY" "$S/profile_ruleset.py" ChinaMax.list          # 规则集类型分布
"$PY" "$S/probe_dns_endpoints.py" Profile.yaml       # 端点逐个实测
"$PY" "$S/probe_doh.py"                              # 只测 DoH 线格式
```

退出码：**0 = 通过**，用于提交前检查（本仓库**不挂 CI**）。
规则集缓存写在系统临时目录（`%TEMP%\egern-ruleset-cache` 或 `/tmp/egern-ruleset-cache`），约 5 MB。
